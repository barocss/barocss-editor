Roadmap · measured 2026-08-14

Barocss Suite

One document engine, several products. Three questions decide whether that is a plan or a wish — and each is answered here from what the repository contains, not from what it could contain.

19 packages ~85,000 lines of source 5 apps 1 product shipped
00

Where this stands

What matters is not the size but the shape. Six layers, each knowing only about the ones beneath it — except where the manifests say otherwise, which is question one.

LayerPackagesKnows about
Substrate shared · dsl · schema Nothing above it
Document datastore · model The schema
Rendering renderer-dom · renderer-react The DSL
Editing editor-core · editor-view-dom · editor-view-react · extensions · dom-observer · text-analyzer The document and a renderer

Every package already declares exports and types, carries a version, and none is private. Nothing structural stops them being published today.

Of those three used as a value — all are type positions missing a keyword

editor-core declares extensions and renderer-dom as dependencies and imports neither. model reaches up to editor-core eleven times, and every one of them is a type. What is left is a naming problem: ModelSelection is a document concept living in the editing layer.

What “React-like” would mean here

React ships one idea — a tree reconciled into a host — and lets the host be a DOM, a canvas, a terminal. This repository already has that shape: dsl is the template language with no host, renderer-dom is one host and renderer-react another, and the document layer is independent of both.

What is not React-like: editor-core assumes a text editor — a caret, a selection, contenteditable. A page builder or a spreadsheet wants the document layer and a renderer and none of that.

02

Can one schema carry all of them?

MEASURED

The schema yes; the renderer and the input no. And the division is not DOM versus canvas — it is whether the browser can be asked where the text goes.

packages/schema already holds three schemas: a general document, Word’s, and a Figma-like one — DOCUMENT → PAGE → FRAME | RECTANGLE | TEXT | COMPONENT, written and marked reference only. Somebody already answered the node-and-attribute half of this question in the affirmative.

ProductSchemaRendererInputLayout
Word done done done done
HTML WYSIWYG (Summernote-like) exists done done —
Schema WYSIWYG (ProseMirror-like) this is that done done —
Pages (Notion-like) additions done done —
Page builder (builder.io-like) additions done new direct manipulation —
Spreadsheet (Excel-like) grid nodes virtualised new 2D ranges row/col sizing
Design tool (Figma-like) reference exists new canvas new new text shaping
Whiteboard (FigJam-like) as Figma as Figma + presence as Figma

Three of these need no new layer at all

Summernote-, ProseMirror- and Notion-like products are the same document, the same DOM renderer and the same input path with a different schema and a different set of extensions. The distance is measured in schemas and commands, not in architecture.

The wall is text shaping, not canvas

The renderer is a day’s work — dsl already separates template from host. The problem is underneath it. The file this engine’s pagination is built on opens by saying so:

“Character widths, kerning, script shaping and line breaking are all already done — Range.getClientRects() hands back one rectangle per line box, which is the line breaking result. Computing glyph metrics ourselves would be re-deriving an answer the layout engine has already given.”
packages/office-word/src/measurement.ts

On a canvas there is no layout engine to ask. Glyph metrics, kerning pairs, bidi, Hangul and CJK line-breaking rules, ligatures — all of it has to be built. It is the single largest piece of work in this document, and a server-side renderer meets the same wall from the other side. Everything else on the canvas side is ordinary.

Which makes one prototype worth doing before committing: a design tool whose text is a DOM overlay dodges the wall entirely, and takes days rather than months to find out.

03

Can each ship as its own program?

MEASURED

Yes, and the repository is already arranged for it. What is missing is not packaging but the seam a product plugs into.

A product here is six things: a schema, a renderer registration, an extension set, a keymap, a toolbar model, and a shell. Five of the six are already data — WORD_TOOLBAR, WORD_KEYBINDINGS, registerWordRenderers, the schema, the extension list. The sixth is written by hand per app, which is why the shell in apps/word is Word’s rather than the kit’s.

word-kit.ts is already close to the contract. Naming it, and building a second app that shares the shell, is what turns one product into a suite.

04

The order, and how to know each worked

Each step is chosen so the next one is cheaper. Phases 1 and 2 are small and unblock everything after them.

  1. Make the graph honest

    Move ModelSelection down into schema or shared, add the three missing type keywords, drop the two phantom dependencies.

    Done when every package builds against only the packages below it and the graph is a DAG.

  2. Split the editing layer

    Separate what any product needs — commands, transactions, history, context, keybindings — from what a text product needs: a caret, a selection, contenteditable coordination.

    Done when a package can use commands, history and transactions without importing anything about a caret.

  3. A second product

    The page builder, on the DOM renderer, sharing the shell. This is the step that proves the core is a core — a library nobody has built a second thing with has one user’s assumptions baked into it.

    Done when the shell belongs to no product, and a feature added to the kit appears in both.

  4. Publish

    Versioning, a stability promise for dsl and schema — the two others would build against — and documentation aimed at somebody who has not read this repository.

    Done when a person outside it builds a third product without asking a question the documentation should have answered.

  5. Decide about canvas

    Prototype text-as-DOM-overlay first. Let that decide whether the shaping engine is worth building — on evidence rather than on appetite. This must not start before phase 3 finishes: building a canvas first would prove only that a canvas can be drawn on.

    Done when the decision is made, either way, with a reason attached.

05

What would make this wrong

Written down so it is checked rather than assumed. Each of these would move a phase, not merely delay one.

  • If the schema cannot express a cell reference. A formula points at another node, and this document model has no notion of one node pointing at another except by id in an attribute. That may be enough. Nobody has tried.
  • If collaboration does not survive the split. collaboration is 535 lines against datastore, and the id namespaces were only unified this month. A second product editing concurrently is its first real test.
  • If the operation harness does not generalise. Every operation has an exact inverse and all four ratchets sit at zero — for this schema. A grid, or a canvas transform, is where that discipline either holds or turns out to have been tuned to one document shape.
