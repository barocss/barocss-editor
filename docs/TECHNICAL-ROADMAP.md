# 기술 로드맵 — MS Office 를 넘어서려면 무엇이 필요한가

`ROADMAP.md` 는 **어디로 가나**를 갖는다. 이 문서는 **무엇을 지어야 거기 닿나**를 갖는다 — 기능 목록이
아니라 *층과 능력*의 목록이고, 각 항목은 **이미 있는 것**과 **없는 것**을 갈라 적는다.

> 이 저장소가 반복해서 배운 것: 대부분의 일은 기능을 짓는 것이 아니라 **스키마가 이미 선언한 것을
> 읽는** 것이었다. 다섯 번 넘게 그랬다. 그래서 모든 항목이 *이미 있는 것을 먼저* 적는다 — 그것이
> 하루짜리 일과 달짜리 일을 가르는 유일한 기준이다.

## 1. 넘어서려면 — Office 가 잘하는 것과, 그것으로 부족한 것

MS Office 를 *따라잡는* 것과 *넘어서는* 것은 다른 일이다. 따라잡기는 기능 목록이고, 넘어서기는
**Office 가 구조적으로 못 하는 것**을 하는 것이다.

### Office 가 구조적으로 못 하는 넷

| | Office 의 한계 | 이 저장소가 이미 가진 것 |
|---|---|---|

#### 제스처 — 스물을 여덟 질문에 대조한 것

`pointerdown` 뒤에 move/up 을 붙이는 자리가 **스물**이고, 같은 질문 여덟 개에 각자 답하고 있었다.
셋은 답이 하나뿐인데 그 하나를 **한 파일만** 썼다:

| 질문 | 답한 곳 |
|---|---|
| `pointercancel` 로 끝날 수 있다 | **스물 중 하나** (`apps/site/grip.tsx`) |
| 리스너는 요소에 붙는다(`window` 아님) | **스물 중 하나** |
| Escape 로 되돌린다 | 스물 중 넷 |
| 오른쪽 버튼은 드래그가 아니다 | 스물 중 둘 |

그리고 이건 정돈이 아니라 **살아 있는 결함**이다. `window` 에 `pointermove` 를 붙이고 `pointerup`
에서만 걷으면, 브라우저가 `pointercancel` 을 주는 순간 — 터치가 끊기거나, 잡고 있던 요소가 드래그
도중 DOM 에서 사라지면 — 그 리스너가 window 에 영원히 남는다. 그 뒤로 상관없는 포인터 움직임이 드래그
계산을 계속 돈다. 화면은 멀쩡하고, 리로드하면 사라지고, 재현 절차를 적을 수 없다.

`shared/gesture.ts` 의 `dragGesture` 가 **`done` 과 `abort` 를 합쳐 정확히 한 번**을 보장하고 어느
쪽으로 끝나든 리스너를 다 걷는다. 검사가 리스너 수를 직접 센다 — 그 결함은 화면에 안 보이므로 세는
것 말고 잡을 방법이 없다.

- [x] `office-ui/stack.tsx`, `apps/slide/layer-panel.tsx`, `apps/slide/paint-panel.tsx`
- [x] `apps/word/ruler.tsx` — **눈에 보이는 결함이 하나 있었다.** React 의 `onPointerMove` 는 버튼을
      누르지 않아도 오므로, 취소된 드래그 뒤에 `dragging.current` 가 남아 그냥 마우스를 올리기만 해도
      마커가 따라다녔다. 놓지 않은 드래그가 화면에 남는 것이다.
- [ ] 남은 열여섯. 위험한 순서로: `slide/overlay`(3) → `slide/timeline`(4) → `word/drawing-overlay`(3)
      → `site/overlay`(3) → `slide/stage`(2) → `office-text/table-selection-view`

### 2.1 엔진 — 거의 다 됐다

- [ ] **선택의 나머지.** 두 끝이 형제가 아닌 범위 — 인용문 안에서 바깥으로 — 는 글자만 맞고 블록은

## 3. 어떤 순서로

각 걸음은 **다음 걸음을 싸게 만드는** 것으로 고른다. 그리고 각 걸음에는 *끝났음을 아는 방법*이 있다.

| # | 무엇 | 끝났음의 기준 | 크기 |
|---|---|---|---|
| 1 | 선택의 남은 둘 | `Shift+→` 가 세 블록을 넘어도 범위가 문서 순서다 | 작음 |
| 2 | 크롬 이주 — `page-frame` → `rail` | `apps/site` 가 그 둘을 import 하지 않는다 | 중간 |
| 3 | `editor-core` 를 둘로 (Phase 2) | 캐럿을 모르는 패키지가 명령과 역사를 쓴다 | 중간 |
| 4 | 크롬 이주 — `inspector` → `overlay` | `<SiteEditor>` 가 패키지에서 나온다 | 큼 |
| 5 | 서비스 층의 첫 조각 — 여러 문서 | 한 앱이 문서 둘을 열고 닫는다 | 중간 |
| 6 | 발행 대상과 저장소 | 사이트 하나가 실제 주소에 나간다 | 큼 |
| 7 | 캔버스 결정 | 시제품이 있고, 결정이 근거로 적혀 있다 | 결정 |

**1·2·3 이 작고 뒤의 모든 것을 푼다.** 4 는 3 이 끝난 뒤가 싸다 — 캐럿을 모르는 코어가 있으면
`inspector` 가 무엇을 의존해야 하는지가 분명해진다.

## 4. 이 문서를 어떻게 유지하나

- **잰 숫자만 적는다.** 0절의 표는 명령 한 줄로 다시 낼 수 있어야 한다.
- **각 항목은 *이미 있는 것*을 먼저 적는다.** 그것이 하루와 한 달을 가른다.
- **끝나면 지우지 말고 `[x]` 로 두고 놀란 것을 한 줄 적는다.** `BACKLOG.md` 에 자세히, 여기엔 한 줄.
- **`ROADMAP.md` 와 겹치면 여기를 지운다.** 저쪽이 *왜*를 갖고 여기는 *무엇*을 갖는다.
