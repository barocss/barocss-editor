# Slides product foundation

기준일: 2026-09-13. 현재 주력은 Wonffice Slides다. S2 자동 저장·복구와 S3-a 장 간 복사·다중 선택을 구현·검증했다. S3-b 작성과 S4 디자인·발표를 범위별로 검증하고 S5 인쇄/PDF를 연결했다. Site 인수 점검으로 이동한다. 사용자 목표는 회사가 하나의 Office에서 업무를 수행할 수 있도록 제품군을 확장하는 것이다. Word의 모든 고급 기능을 완료할 때까지 Slides를 미루지 않는다. 진행 순서는 Slides → Site → 통합 서비스다.

## 완료 기준과 범위

사용자 확인 방식: 기능을 구현할 때마다 실행 중인 앱에 반영하고, 인앱 브라우저를 표시한 상태에서 실제 조작을 확인한다. 자동 검사 결과와 화면에서 확인한 결과를 구분해 기록한다. 마지막 검증 문서는 브라우저에 열어 둔다.

새 발표 자료에서 슬라이드 구성, 텍스트·그림·도형 편집, 테마·레이아웃, 저장·재열기, 발표·출력까지 끝낼 수 있어야 한다. 기능 수나 명령 등록 수는 제품 완료의 근거가 아니다. 기존 office-slides를 개선하며 새 편집 엔진을 만들지 않는다.

- 기본 UI와 아이콘: office-ui / office-icons.
- 편집 명령 컨트롤과 파일 UI: office-controls / office-editor-ui.
- 텍스트 입력과 서식: office-text 및 공통 editor core/view.
- 객체 기하·선택·리사이즈: office-canvas.
- 슬라이드·마스터·테마·발표·모션: office-slides.
- 저장 기반: 공통 documentLibrary를 재사용하되 기존 Slides 파일/라이브러리 이름과 향후 전역 문서 ID를 구분한다.

## 단계

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| S1 | 기존 제품 인수·저장 실패 처리 | 작성·파일 교환·라이브러리·발표 기준 검사, 오류 후 원본 보존과 재시도 |
| S2 | 자동 저장·복구 | 안정적 문서 ID, 마지막 입력 저장, 재열기, 충돌 초안, 실패 재시도, 문서 전환 전 저장 |
| S3 | 작성·객체 편집 | 새 문서의 한글 입력·삭제·붙여넣기·서식, 추가·복제·재정렬, 이동·크기·정렬·그룹·레이어·undo |
| S4 | 테마·레이아웃·발표 | 콘텐츠 보존, 테마/레이아웃 적용, 노트·발표자 화면·전환, 확대율별 편집 |

PPTX 완전 호환, 차트 데이터, 고급 애니메이션, 모바일·접근성·성능 및 실시간 협업은 별도 범위다. 기존 JSON 파일 저장을 PPTX 지원으로 표시하지 않는다. 계정·팀·권한·서버 저장·통합 탐색은 제품별 로컬 편집과 분리해 통합 서비스 단계에서 완성한다.

## S1 인수 점검

기존 Slides는 파일 다운로드/열기와 이름 기반 로컬 라이브러리 저장을 제공한다. 자동 저장·자동 재열기·충돌 초안·복구가 완료된 상태는 아니다. 다음 구현 우선순위는 S2다.

라이브러리 열기 중 저장소 읽기 실패를 재현했다. 이전에는 처리되지 않은 실패가 발생하고 재시도 안내가 없었다. 이제 현재 덱을 유지하고 오류와 재시도 안내를 표시한다. 다음 열기가 성공하면 오류를 지운다. 실패 후 원본 보존, 처리되지 않은 오류 없음, 재시도 성공을 브라우저 검사에 추가했다.

명세의 오래된 측정값도 실제 검사 결과에 맞췄다. 64 노드 / 527 속성, 총 191 명령, 앱 2,527행이며 Word 인용은 108 노드 / 1,043 속성이다. 이는 기능 추가 실적이 아니라 문서 정정이다.


검증: Slides 단위 1,046/1,046 통과. 최초에는 오래된 명세 수치로 5개가 실패했고 실제 측정값을 반영한 뒤 전체 통과했다. 라이브러리 읽기 실패 회귀는 수정 전 실패, 수정 후 통과했다. 핵심 Chromium 최종 42/42 통과: 파일 저장/열기/새 자료, 라이브러리 정체성·재시도, 객체 이동/크기/삭제/undo, 텍스트·노트 입력, 발표자 화면과 창을 포함한다. 최초 브라우저 실행 중 라이브러리 닫기 대기 1건이 실패했다. 당시 소스 수정이 진행 중이었으므로 동일 소스의 최종 전체 실행으로 재검증했다. 원인을 확정한 것으로 표시하지 않는다. Vite 빌드 통과(기존 큰 청크 경고). 전체 TypeScript는 기존 공통 소스 오류로 실패하며 변경한 library-dialog 진단은 없다.

실제 앱: http://localhost:5181/ 에서 보고 템플릿 5장을 만들고 제목을 “하나의 Office”로 편집했다. 라이브러리에 “하나의-office”로 저장된 5장 항목을 확인했다. 발표 시작, 오른쪽 키로 2장 이동, 왼쪽 키 복귀, Esc 종료를 확인했다. 편집 화면을 브라우저에 열어 두었다. 이는 입력·수동 저장·발표 확인이며 자동 저장·복구 완료를 뜻하지 않는다.

다음 구현: S2 자동 저장·복구. 이후 S3–S5를 거쳐 Site로 주력을 옮긴다. Word의 고급 DOCX 후속 작업이 이 순서를 막지 않는다.


## S2 — 자동 저장·복구: 2026-09-13

Wonffice Slides의 작업 자료에 안정적인 URL 식별자(`#slides=...`)와 300ms 지연 자동 저장을 연결했다. 새로고침하면 해당 작업 자료를 다시 연다. ‘최근 자료’에서 자동 저장한 자료를 고르고, 충돌 초안을 새 자료로 복구한다. 저장 상태, 저장/복원 재시도 버튼을 표시한다. 복원할 자료가 없으면 URL을 유지하며 샘플로 덮어쓰지 않는다.

공통 `DocumentSaveQueue`는 documentLibrary의 조건부 revision 쓰기와 직렬 처리를 담당한다. 저장 도중 새 편집이 발생하면 다음 스냅샷에 새 revision을 전달한다. 쓰기 실패는 재시도할 때까지 메모리에 유지한다. 다른 탭이 원본을 먼저 갱신하면 별도 recovery 저장소에 현재 작업을 보관하며, 후속 편집도 같은 초안을 갱신한다. 복구는 새 ID를 만들며 최신 원본과 초안 원본을 모두 유지한다. 최신 원본을 명시적으로 다시 열면 기존 충돌 상태를 해제한다.

제품 어댑터 DeckAutosave는 Slides 파일 포맷, 제목·장 수, 콘텐츠 이벤트, URL과 전환을 맡는다. office-ui 기반 SlideDocuments와 useSlidePersistence는 office-slides/ui에서 제공한다. Word/Note의 기존 저장 컨트롤러는 이번에 교체하지 않았다. 저장 큐는 향후 다른 제품도 사용할 수 있는 공통 모듈이다.

기존 이름 기반 덱 라이브러리는 자산 사본/덱 링크용으로 유지한다. 자동 저장 작업은 별도의 workspace 저장소를 사용한다. 라이브러리나 외부 파일을 열면 독립적인 작업 ID로 저장한다. 라이브러리 사본을 갱신하려면 기존 라이브러리 저장을 사용한다. 이 단계는 전역 회사 문서 ID나 서버 동기화가 아니다.

새 자료·파일 열기·템플릿·라이브러리 열기·발표 중 외부 덱 이동은 기존 작업의 저장을 먼저 확인한다. 실패하면 전환하지 않는다. 저장/읽기 대기 중 소스 편집 또는 다른 열기가 발생하면 지연된 열기는 내용을 교체하지 않는다. 저장 전 브라우저 종료에는 경고를 표시하지만 강제 종료/OS 중단 시 아직 쓰지 못한 입력의 복원은 보장하지 않는다.

검증: Slides 단위 1,046/1,046, 공통 저장 큐·라이브러리 단위 23/23, Chromium 51/51, Vite 빌드 통과. 새 브라우저 검사는 입력 후 복원·템플릿 전환·원본 재열기, 두 탭 충돌과 새 자료 복구, 쓰기 실패 시 전환 차단 및 재시도, 없는 ID 보호를 포함한다. 초기 두 비교는 세션 sid/loadedAt까지 비교하여 실패했다. 저장 대상 콘텐츠·속성 비교로 수정한 뒤 전체 통과했다. 전체 TypeScript는 기존 공통 소스 오류가 남아 있으며 이번 저장 관련 소스 진단은 없다. 빌드는 기존 청크 크기 경고를 포함한다.

실제 앱: http://localhost:5181/#slides=99e80764-7ffb-446b-85f1-eb3ef84d9c2b. 기존 ‘하나의 Office’ 라이브러리 5장 자료를 열고 발표자 노트에 ‘Wonffice 제품군을 하나의 작업 공간으로 연결합니다.’를 입력했다. 최근 자료 목록, 저장됨 상태, 새로고침 후 5장·제목·노트 복원을 확인했다. 브라우저를 이 자료에 열어 두었다.

다음은 S3: 새 자료의 한글·붙여넣기·서식과 객체 선택/이동/크기/정렬의 실제 작성 흐름을 점검한다. S4 테마/발표, S5 출력/교환을 거쳐 Site로 이동한다. PPTX 완전 호환이나 서비스 출시 완료를 뜻하지 않는다.


## 2026-09-13 — S3 편집 화면 정리

- 선택된 슬라이드의 왼쪽 강조선을 제거하고 네 면이 같은 테두리로 표시한다.
- 눈금자와 슬라이드를 내용 크기 기준의 동일 격자에 놓는다. 여유 공간은 격자 전체를 가운데 정렬한다. 확대 시 스크롤 원점은 접근 가능하게 유지한다.
- 가로·세로 눈금자를 24px로 맞추고 숫자를 눈금 선 밖에 배치해 잘림을 없앴다. 화면 맞춤 계산도 같은 두께를 사용한다.
- office-ui `PropertyPanel`에 `density="comfortable"` 옵션을 추가했다. 288px 폭, 30px 입력칸, 명확한 그룹 제목·간격·입력 테두리, 네 면의 선택 탭을 공통 토큰으로 제공한다. Slides가 이 옵션을 사용한다. office-controls 선언 → PropertySheet → 편집 명령 연결과 office-editor-ui 선택 갱신은 유지한다.
- Chromium 관련 42개 검사 통과(재검증 포함). 확대율 40/100/150%, 화면 1280×720 및 1440×1000에서 눈금자 좌표·인접 배치·숫자 영역을 추가 검증했다. 안내선 드래그, 휠 확대 중심, 마스터/레이아웃, 다중 선택 속성 변경도 확인했다.
- Vite 빌드 통과. office-ui 단위 검사 115개 통과, 기존 math-integrations 스타일 등록/가져오기 감사 2건 실패. 이번 작업에서 수식 패키지는 변경하지 않았다.
- 실제 브라우저의 기존 5장 자료에서 슬라이드 선택 표시, 눈금자, 제목 객체 선택 및 오른쪽 속성 패널을 확인했다.

S3 전체 완료는 아니다. 다음은 실제 새 자료 작성에서 한글 입력·붙여넣기·서식과 객체 조작을 연결해 검증한다.


### 같은 날 수정 — 눈금자는 문서가 아니라 뷰포트에 고정

사용자 확인에 따라 앞선 문서 가장자리 배치를 교체했다. 현재 구현 기준은 편집 뷰포트 위쪽·왼쪽에 고정된 24px 눈금자다. 슬라이드만 별도 영역에서 스크롤한다. 눈금자의 0점·눈금·포인터는 실제 슬라이드 위치와 확대율을 따라 이동한다. 안내선 드래그는 뷰포트 좌표에서 슬라이드 원점을 빼서 문서 좌표로 변환한다.

Chromium 39개 통과: 두 화면 크기, 40/100/150% 확대, 양방향 스크롤, 눈금자의 고정 위치와 문서 좌표 일치, 안내선, 마스터/레이아웃 및 발표자 화면. 실제 열린 자료에서도 50%와 100%를 전환해 고정 배치를 확인했다. Vite 빌드 통과.


## 2026-09-13 — 왼쪽 탐색 패널 통합

왼쪽은 자료·객체 탐색, 가운데는 편집 뷰포트, 오른쪽은 선택 객체 속성으로 역할을 나눈다. Figma Slides 공식 화면 안내의 영역 구분을 참고했다: https://help.figma.com/hc/en-us/articles/24170630629911-Explore-Figma-Slides . Canva의 Position/레이어 안내도 확인했으나 동일 배치를 복제하지 않았다.

- `SlideSidebar`가 Filmstrip과 LayerPanel을 하나의 240px 열에 구성한다. 별도 레이어 열기 띠를 제거했다.
- office-ui RibbonTabs의 panel 표시 옵션으로 슬라이드/레이어를 전환한다. 좌우 방향키와 Home/End를 지원하며 선택 탭은 네 면의 테두리를 사용한다.
- 슬라이드 탭: 176px 썸네일, 번호·이름, 전체 장 수. 레이어 탭: 현재 슬라이드 선택창, 공통 객체 아이콘, 선택·숨김·잠금·순서 변경.
- 두 목록은 탭 전환 중 유지한다. 캔버스 폭·확대율·객체 선택·썸네일 스크롤 위치가 바뀌지 않는다.
- Chromium 37개 통과: 탭 상태, 키보드 전환, 레이어 탭 내 슬라이드 이동, 선택/잠금/숨김/재정렬, 컴포넌트 선택, 뷰포트 눈금자, 발표자 화면. 레이어 모델·스펙 단위 28개 및 Vite 빌드 통과.
- 실제 기존 5장 자료에서 슬라이드/레이어 탭 전환과 제목 레이어 선택 → 오른쪽 속성 연결을 확인했다.

S3 작성·객체 편집은 계속 진행한다. 자산/컴포넌트 패널의 추가 통합은 후속 설계 범위다.

## 2026-09-13 — 다중 슬라이드 편집 가능 범위 확인

사용자 요청은 Figma처럼 여러 슬라이드를 같은 작업 공간에서 편집할 수 있는지 확인하는 것이다. 현재 전체 보기는 모든 슬라이드를 세로로 나열한다. 모든 문서는 하나의 편집기 모델에 있으므로 두 번째 슬라이드의 텍스트에도 편집 진입이 가능하다. 그러나 SelectionOverlay는 `current` 한 장에만 연결되며, 전체 보기에서 다른 장의 본문을 클릭해도 `current`를 갱신하는 연결이 없다.

검증: 사용자 자료와 분리된 Chromium에서 샘플 6장을 전체 보기로 열고 40%로 설정했다. 두 번째 슬라이드 제목에 `MULTI-CHECK`를 입력했다. 두 번째 제목만 변경됐고 첫 번째 장은 유지됐지만, 페이지 표시는 `1 / 6`에 남았다. 사용자 브라우저에서는 기존 5장 자료를 전체 보기로 열고 두 번째 제목에 편집 진입했으며, 사용자 자료의 텍스트는 변경하지 않았다.

현재 판단: 여러 장 표시·각 장의 텍스트 편집은 부분 지원한다. 그리드 작업 화면, 활성 장 자동 동기화, 장 사이 객체 드래그 및 서로 다른 장의 객체 동시 선택은 제품 수준 지원으로 판정하지 않는다. 이번 작업은 가능 범위 확인이며 해당 기능 구현 완료를 뜻하지 않는다.

S3 다음 우선순위:
1. 다른 장을 클릭하면 활성 장·레이어·속성·노트·객체 삽입 대상이 함께 변경되어야 한다.
2. 한 장 보기와 여러 장 작업 보기를 구분한다. 여러 장 작업 보기는 격자 배치와 확대·이동을 제공한다. 화면 배치 좌표와 슬라이드 문서 좌표를 분리한다.
3. 장 사이 복사·이동은 대상 장, 위치, undo와 저장·재열기를 함께 검증한다.
4. 서로 다른 장의 객체를 동시에 선택해 공통 서식을 적용하는 기능은 별도 단계로 구현한다. 선택 상자와 각 장 좌표의 변환을 먼저 정의한다.


## 2026-09-13 — S3 자유 캔버스와 편집 대상 동기화

앞선 다중 편집 점검에서 발견한 활성 장 불일치를 수정했다. 다른 장의 객체 클릭, 텍스트 편집과 커서 이동은 `current`를 갱신한다. 왼쪽 탐색, 페이지 번호, 객체 삽입, 레이어, 속성, 발표자 노트가 이 활성 장을 공유한다.

- 기존 세로 나열을 `캔버스 보기`로 교체했다. 초기 배치는 두 열이며, 제목을 끌어 양 축 어디로든 옮길 수 있다. 한 장 보기와 발표는 기존 문서 좌표를 사용한다.
- `surface.canvasX/canvasY`는 작업 공간의 CSS px 좌표다. Stage만 배치에 사용한다. 슬라이드 내부 객체 좌표와 발표 순서를 변경하지 않는다. `setSlideInfo` 한 번으로 저장하고 한 번에 실행 취소한다. 잘못된 숫자는 거부한다.
- 휠로 양방향 화면 이동, Ctrl/Cmd+휠로 포인터 중심 확대·축소, Space+드래그 또는 가운데 버튼 드래그로 화면 이동을 제공한다. 카메라 변환은 문서 변경 이력에 기록하지 않는다. 변환 후 선택 오버레이도 새 화면 위치를 읽는다.
- `office-ui` PropertyPanel에 inspector 밀도를 추가했다. Slides 패널 폭 280px, 입력 높이 28px, 그룹 간격을 사용한다. 공통 PropertySheet에서 모서리 네 값을 묶고 속성 그룹 접기를 제공한다. 캔버스 제목도 공통 Button을 사용한다.
- 완료 범위: 자유 배치와 한 장씩 편집하는 활성 문맥. 장 사이 객체 드래그 이동, 여러 장의 객체 동시 선택·일괄 서식, 대규모 덱 가상화는 후속 범위다.

검증 결과:
- 단위 61개 통과: 슬라이드 명령, 스키마, 명세 수치, 렌더링 계약 감사. 작업 공간 좌표는 Stage에서 소비하므로 정적 슬라이드 렌더러 감사에는 소비 지점과 검증 근거를 기록했다.
- Chromium 고유 30개 통과: 자유 캔버스 3개, 기존 편집·화면 24개, 공통 UI 3개. 최종 자유 캔버스 검사는 다른 장의 텍스트 편집·객체 삽입, 제목 드래그, undo/redo, 저장·새로고침 복원, 양방향 pan, 선택 오버레이 정합성, 확대를 포함한다.
- 배치 복원 검사는 재열기 전 sid를 사용하면 초기 샘플의 옛 노드를 읽는다. 재열기 후 표시된 슬라이드의 sid로 검사해 복원을 확인했다. 파일 저장은 세션 sid를 제거한다.
- Vite 빌드 통과. 전체 TypeScript 검사는 기존 다른 패키지 오류로 통과하지 않는다. 이번 수정 소스의 오류는 검출되지 않았다.
- panel-model 브라우저 검사는 수집 단계에서 math-editor locale JSON의 Node import 속성 오류로 실행되지 않았다. 공통 UI 검사와 실제 속성 패널의 선택·접기는 별도로 확인했다.
- 실제 기존 5장 자료를 캔버스로 열고 두 번째 제목을 클릭했다. 페이지 2/5, 왼쪽 선택, 제목 상자 속성, 두 번째 발표자 노트가 함께 바뀌었다. 속성 그룹 접기도 확인했다. 자료 본문은 수정하지 않았다.

## 2026-09-13 — S3 장 사이 객체 이동

캔버스 보기에서 선택한 최상위 객체를 다른 장으로 끌어 이동한다. 대상 장과 이동할 위치를 화면에 미리 표시한다. 객체 ID와 그룹 내부 구조를 유지하며, 좌표를 대상 장의 문서 좌표로 변환한다. 이동은 한 번의 실행 취소로 복원한다. undo/redo 뒤 활성 장·속성도 객체가 속한 장을 따른다. Escape와 pointercancel은 이동을 취소한다.

`moveBoxesToSlide` 명령은 잠김·바인딩·잘못된 좌표와 여러 출발 장을 거부한다. 그룹 전체 이동은 가능하며 그룹 내부 객체만 꺼내는 동작은 후속 범위다. 다른 장의 객체를 참조하는 연결선 이동은 거부한다. 원래 장에 남는 연결선은 이동 객체를 향하던 끝점을 고정한다. 선택 미리보기는 viewport portal로 표시해 원래 장 경계에서 잘리지 않게 한다.

검증: 명령·명세·conformance 단위 58개, 새 이동/취소와 기존 자유 캔버스·편집 Chromium 16개, Vite 빌드 통과. 객체 구조·좌표·undo/redo·저장/재열기를 확인했다. 전체 TypeScript에는 다른 패키지의 기존 오류가 남아 있고 이번 변경 소스 진단은 없다. 빌드의 기존 큰 청크 경고도 남아 있다.

실제 열린 사용자 자료에서 첫 장의 ‘하나의 Office’ 제목을 두 번째 장으로 이동했다. 활성 장 2/5와 속성 좌표 변경을 확인했다. 실행 취소 후 제목의 원래 위치와 활성 장 1/5를 확인했으며 자료 내용을 원상 복원했다.

다음: 장 사이 복사, 여러 장의 객체 동시 선택·공통 서식. 이후 S3 작성 흐름 마감 → S4 테마/발표 → S5 출력/교환 순서로 진행한다. S3 전체 완료나 서비스 출시 완료로 판정하지 않는다.
